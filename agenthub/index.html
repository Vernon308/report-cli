AGENT AS TEAMMATES · WORKSPACE AS SHARED CONTEXT丁群 · 2026
我们先从一个很日常的问题开始：如果要做一个小产品，通常得先理清需求，再设计界面、写代码、检查结果。今天这些工作可以交给不同的 AI Agent，但只把它们放在几个独立的聊天窗口里，协作仍然要靠人来回搬运上下文、转交文件、盯进度。AgentHub 想解决的就是这段断开的协作过程。它把 Agent 作为可选择的成员，把一次对话作为共同工作的空间，再让 Orchestrator 帮忙拆解和调度。重点不是 Agent 数量多，而是它们能围绕同一个目标接力工作。
01 / START WITH INTENT

一句需求，
先别急着开工

把真正影响方案的选择摆到桌面上，先对齐“要做成什么”。

  • 范围：基础版还是完整版本？
  • 体验：移动优先，还是桌面优先？
  • 验收：哪些页面和能力必须具备？
好的协作，往往从一个合适的问题开始。
Orchestrator 把不确定性变成可回答的问题02 / 09
02 / 09
截图里用户说的是“做一个记账 App”。这句话看起来清楚，真要动手却还缺不少信息：做基础记账还是完整版本？优先支持什么设备？需要哪些页面？要不要统计和分类管理？AgentHub 让 Orchestrator 先识别这些会影响方案的关键选择，再把问题集中交给用户。用户回答之后，Orchestrator 再把目标整理成任务和验收标准，而不是让每个 Agent 各自猜一遍。协作质量不只取决于模型会不会写，还取决于系统能不能把模糊意图变成共享、可检查的工作约定。
02 / MAKE THE PLAN VISIBLE

计划先给人看，
再让 Agent 执行

每一项工作都有负责人、依赖关系和可检查的交付目标。

  • 产品经理先写 PRD
  • 前端工程师依据 PRD 实现
  • 用户确认、拒绝，或在对话里修改计划
把方向校准放在执行成本之前。
两个任务，一条明确依赖：先 PRD，后实现03 / 09
03 / 09
这里可以看到 Orchestrator 把工作拆成了两个任务：产品经理先输出 PRD，前端工程师再根据 PRD 实现应用。第二项依赖第一项，所以不是简单地把两个任务同时扔出去。计划以卡片展示出来，用户可以执行、拒绝，也可以直接在聊天里提出修改意见。修改意见仍然留在对话里，Orchestrator 据此重新规划。计划确认后系统再启动执行，这让“谁做什么、依赖什么、做到什么程度算完成”都能被看见。把计划放在执行之前，是为了让人能在成本真正花出去之前校准方向。
03 / KEEP WORK IN ONE PLACE

任务在接力，
上下文不掉队

聊天、状态与成果都留在同一个会话，成员能看到工作如何往前走。

  • 产品经理交付，前端工程师接手
  • 用户随时查看、补充、纠偏
  • 不必在工具之间反复搬运资料
聊天是过程，产物是可以接手的工作成果04 / 09
04 / 09
执行开始后，不需要用户在不同工具之间复制粘贴。群聊里能看到 Orchestrator、产品经理和前端工程师各自的消息，任务卡片显示状态，产物也作为独立对象出现在会话里。产品经理完成 PRD，前端工程师可以沿着依赖关系继续实现；用户则能在过程中查看文档、提出修改，或者发现方向不对时及时叫停。对团队来说，这种可见性很实际：不必只等最后一个“已完成”，也不用猜某个 Agent 到底拿到了什么上下文。每个参与者的工作结果和后续接力关系，都留在共同的工作现场。

不同 Agent，走同一条协作流水线

把平台差异留在适配层，让一次运行从服务端到界面都有清楚的路径。

为什么要这样分层？接入新平台时，界面不用跟着理解它的私有协议。
05 / 09
从工程上看，AgentHub 把界面、状态传输、应用服务、Agent 平台适配器和持久化分成几层。用户发出消息之后，由 AgentRunner 管理一次运行的生命周期；底层适配器负责接上 Claude Code、Codex 或自建 Agent，并把平台各自不同的输出翻译成统一的 StreamEvent。服务层处理这些事件、保存消息和产物，再通过一条 SSE 连接推给前端，前端更新对应会话。新增一种 Agent 平台时，不必让 UI 跟着理解它的私有协议。Orchestrator 本身也是走同一个 AgentRunner 的特殊 Agent，它靠额外工具承担调度，而不是另起一条难以维护的执行通道。

WORKSPACE

支持沙箱与本地项目目录
把“会调用模型”延伸成能进入任务、使用工具、留下成果。
06 / 09
这条流水线接入了 Claude Code、Codex、自建 Agent 和开发期的 Mock；也可以登记本地 Daemon，把任务交给 Claude Code 或 OpenCode 等运行端。Agent 不只生成文字，还能在工作区里读写文件、运行命令、读取产物、提出问题或拆任务。工具调用由应用服务集中执行，结果再回到会话。不同会话各自保留上下文和工作空间，几项工作可以并行推进，做出来的文档、代码和网页也能留在当前任务里继续交接。

讨论留在消息里，成果留在工作区。每次修改可以继续形成版本
文档网页代码版本

07 / 09
消息记录讨论过程，产物有自己的类型、版本和生命周期。截图中的交付总结列出 PRD 与记账应用，右侧直接预览网页；文档、网页、图片、代码等可以继续预览或编辑，修改会形成新的版本。后续 Agent 也能通过产物引用继续读取内容，不必从整段聊天里重新找材料。这样交付的不只是一句“已经做好”，而是工作空间中找得到、看得见、能比较、也能继续改的成果。
07 / AUTOMATION WITH BOUNDARIES

自动化要跑得快，关键决定仍要看得见

把确认点、执行范围和完成条件做成流程的一部分。

01

计划由人确认

拆分后先审阅；执行、拒绝或用自然语言要求修订。

02

结果按约定检查

任务带着验收标准；完成状态要对应可检查的结果。

03

工具受工作区约束

文件读写与命令在工作区规则内运行，可接入本地环境。

项目按本地形态运行；关键控制点落在计划审批、工作区边界和验收流程里。

HUMAN IN THE LOOP
08 / 09
Agent 越能做事，越需要清晰的边界。AgentHub 的规划流程保留用户确认点：先看计划，再决定是否执行，也能拒绝或要求修改。任务可以带验收标准，最终结果会按这些标准检查，而不是只看 Agent 自己说“做完了”。对工作区操作，文件读写和命令执行要经过沙箱规则；运行端可以接入本地环境。关键控制点落在具体流程里：哪些任务要跑、谁来跑、在哪个目录操作、结果是否符合约定，都尽量不藏在黑盒里。

09 / 09
总结一下，AgentHub 关注的不是让每个 Agent 单独变得更聪明，而是让多个 Agent 围绕共同目标协作时，需求、计划、执行过程和成果都能接得上。用户提出目标，Orchestrator 帮忙澄清并拆分工作，用户确认后由合适的 Agent 接力执行，最后把结果交付成可查看、可修改的产物。我们希望把人从反复搬运上下文、追问进度和拼装结果里解放出来，让人更多地做目标判断、关键取舍和最终验收。AgentHub 已把会话协作、任务编排、多种 Agent 接入和产物预览连成闭环。接下来要继续打磨的是：让这个闭环在更复杂、更真实的任务里依然清楚、稳定、可控。
