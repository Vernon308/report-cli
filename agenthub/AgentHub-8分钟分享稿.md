# AgentHub：让多个 Agent 像一个团队一样协作

> **用途**：约 8 分钟项目分享；汇报人：丁群；可直接拆成 HTML 幻灯片。  
> **叙事主线**：从“一个 Agent 能做什么”走到“多个 Agent 怎样把一件事交付好”。  
> **建议节奏**：9 页，约 8 分钟；每页屏幕只留要点，口述稿放演讲者备注。HTML 初稿见同目录 `AgentHub-8分钟分享.html`。  
> **配图来源**：`/Users/dingqun/Documents/code/agenthub/assert/`。截图呈现的是 AgentHub 中一次记账 App 示例协作过程，属于产品界面示例，不代表平台只服务记账场景。

## 一句话开场

今天想介绍的不是“又一个能聊天的 AI 页面”，而是一个把多个 Agent 放进同一工作空间、让它们能分工并交付结果的平台。我们把它叫 AgentHub。理解它最简单的方式是：Agent 像联系人，对话像工作空间，Orchestrator 像群里的项目经理。

## 幻灯片 1｜从单个助手，到一支能协作的队伍

**时间**：0:00–0:50  
**画面文案**：

- Agent 是联系人
- 对话是工作空间
- Orchestrator 负责组织协作

**配图**：`assert/6.png`，突出左侧 Agent 列表：UI 设计师、Orchestrator、前端工程师、Reviewer、产品经理。

**口述稿**：

我们先从一个很日常的问题开始：如果要做一个小产品，通常得先理清需求，再设计界面、写代码、检查结果。今天这些工作可以交给不同的 AI Agent，但只把它们放在几个独立的聊天窗口里，协作仍然要靠人来回搬运上下文、转交文件、盯进度。AgentHub 想解决的就是这段断开的协作过程。它把 Agent 作为可选择的成员，把一次对话作为共同工作的空间，再让 Orchestrator 帮忙拆解和调度任务。重点不是 Agent 数量多，而是它们能围绕同一个目标接力工作。

**转场**：那这支队伍是怎么从一句需求走到一份可执行计划的？

## 幻灯片 2｜先把需求问清楚，再开始干活

**时间**：0:50–1:40  
**画面文案**：

1. 用户提出目标
2. Orchestrator 澄清关键约束
3. 生成计划，等待确认

**配图**：`assert/1.png`，用框或放大动画强调结构化澄清问题；屏幕上可只裁切中间弹窗。

**口述稿**：

截图里用户说的是“做一个记账 App”。这句话看起来清楚，真要动手却还缺不少信息：做基础记账还是完整版本？优先支持什么设备？需要哪些页面？要不要统计和分类管理？AgentHub 让 Orchestrator 先识别这些会影响方案的关键选择，再把问题集中交给用户。这样做看起来多了一步，但能减少后面返工。用户回答之后，Orchestrator 再把目标整理成任务和验收标准，而不是让每个 Agent 各自猜一遍。这里体现的一个产品判断是：协作质量不只取决于模型会不会写，还取决于系统能不能把模糊意图变成共享、可检查的工作约定。

**转场**：需求有了边界，下一步就是把它拆成合适的工作包。

## 幻灯片 3｜计划不是一句“我来处理”，而是可读、可改、可确认

**时间**：1:40–2:30  
**画面文案**：

- 产品经理：整理 PRD 与验收标准
- 前端工程师：根据 PRD 实现页面
- 依赖关系：先有 PRD，再开始实现
- 用户确认后再执行

**配图**：`assert/2.png`，突出“计划待确认”卡片和 t1 → t2 依赖；尽量裁掉无关聊天区域。

**口述稿**：

这里可以看到 Orchestrator 把工作拆成了两个任务：产品经理先输出 PRD，前端工程师再根据 PRD 实现应用。第二项依赖第一项，所以不是简单地把两个任务同时扔出去。计划以卡片展示出来，用户可以执行、拒绝，也可以直接在聊天里提出修改意见。比如可以要求把统计页面改成图表，或者先做移动端优先。修改意见仍然留在对话里，Orchestrator 据此重新规划。计划确认后系统再启动执行，这让“谁做什么、依赖什么、做到什么程度算完成”都能被看见。把计划放在执行之前，是为了让人能在成本真正花出去之前校准方向。

**转场**：确认之后，真正的协作过程也留在同一个空间里。

## 幻灯片 4｜一个空间里，看见任务如何接力

**时间**：2:30–3:20  
**画面文案**：

- Agent 各自承担任务
- 进度、消息与产物留在同一会话
- 用户随时能介入、补充或纠偏

**配图**：`assert/3.png`，体现群聊中的不同 Agent、任务状态和右侧产物预览。重点可以落在“PRD 已写入，前端接着实现”。

**口述稿**：

执行开始后，不需要用户在不同工具之间复制粘贴。群聊里能看到 Orchestrator、产品经理和前端工程师各自的消息，任务卡片显示状态，产物也作为独立对象出现在会话里。产品经理完成 PRD，前端工程师可以沿着依赖关系继续实现；用户则能在过程中查看文档、提出修改，或者发现方向不对时及时叫停。对团队来说，这种可见性很实际：不必只等最后一个“已完成”，也不用猜某个 Agent 到底拿到了什么上下文。每个参与者的工作结果和后续接力关系，都留在共同的工作现场。

**转场**：但多 Agent 不是“多开几个聊天框”。真正让它可靠的，是背后把事件、运行和数据串起来。

## 幻灯片 5｜背后是一条统一的协作流水线

**时间**：3:20–4:30  
**画面文案**：

`界面 → 状态 / SSE → 应用服务 → Agent 适配器 → 数据与工作区`

旁注：一套 StreamEvent；一个 AgentRunner；多种 Agent 平台。

**配图**：本页建议自绘简洁流程图；截图可做淡化底图或右下角小窗。流程方向可画成：用户消息 → AgentRunner → Adapter → StreamEvent → 持久化 / SSE → 前端状态更新。

**口述稿**：

从工程上看，AgentHub 把界面、状态传输、应用服务、Agent 平台适配器和持久化分成几层。用户发出消息之后，由 AgentRunner 管理一次运行的生命周期；底层适配器负责接上 Claude Code、Codex 或自建 Agent，并把平台各自不同的输出翻译成统一的 StreamEvent。服务层处理这些事件、保存消息和产物，再通过一条 SSE 连接推给前端，前端更新对应会话。这个设计的好处是新增一种 Agent 平台时，不必让 UI 跟着理解它的私有协议；新增一种事件，也有明确的契约可以让服务端和前端一起演进。还有一个重要的约束：Orchestrator 本身也是走同一个 AgentRunner 的特殊 Agent，它靠额外工具承担调度，而不是另起一条难以维护的执行通道。

**转场**：这套流水线产生的不只是聊天记录，还有能继续使用的工作成果。

## 幻灯片 6｜接得进来，也要能在自己的工作区里做事

**时间**：4:30–5:25  
**画面文案**：

- 适配器：Claude Code、Codex、自建 Agent、Mock
- 运行端：本地 Daemon，可接 Claude Code、OpenCode
- 工具箱：读写文件、执行命令、读产物、提问题、拆任务
- 工作空间：每个会话保留自己的上下文和文件范围

**配图**：建议用 `assert/6.png` 的 Agent 库列表作侧图，或完全采用 HTML 中的四栏图文排版。此图在 HTML 封面已使用；若需要严格避免重复，可将封面改为 AgentHub 字标。

**口述稿**：

这条流水线接入了 Claude Code、Codex、自建 Agent 和开发期的 Mock；也可以登记本地 Daemon，把任务交给 Claude Code 或 OpenCode 等运行端。Agent 不只生成文字，还能在工作区里读写文件、运行命令、读取产物、提出问题或拆任务。工具调用由应用服务集中执行，结果再回到会话。不同会话各自保留上下文和工作空间，几项工作可以并行推进，做出来的文档、代码和网页也能留在当前任务里继续交接。

**转场**：对 AgentHub 来说，协作过程和工作结果是两种不同的东西。

## 幻灯片 7｜聊天负责协作，产物负责交付

**时间**：5:25–6:10  
**画面文案**：

- 文档、网页、代码等作为独立产物
- 可预览、编辑、保留版本
- 结果能继续迭代，而不止“回答完毕”

**配图**：只用 `assert/5.png`，展示产物库与网页预览。原 `assert/4.png` 与它内容高度相似，已从本页和收尾页的截图方案中移除，避免重复展示同一交付界面。

**口述稿**：

这里的一个关键区分是：消息和产物不是一回事。消息记录讨论过程，产物有自己的类型、版本和生命周期。截图中的交付总结列出 PRD 与记账应用，右侧直接预览网页；在 AgentHub 的产物体验里，文档、网页、图片、代码等可以继续预览或编辑，修改会形成新的版本。这样做的意义不只是界面整齐，而是让协作结果可以被接手、比较和继续加工。对使用者来说，交付不再是一长段聊天里的一次性回答，而是工作空间中找得到、看得见、能继续改的东西。

**转场**：结果能不能交付，还取决于人能不能守住关键决策和执行边界。

## 幻灯片 8｜让自动化有边界，让人保留决定权

**时间**：6:10–7:00  
**画面文案**：

- 计划执行前由用户确认
- 任务结果按验收标准检查
- Agent 文件与命令操作受工作区约束
- 本地运行，数据和工作区留在自己的环境

**配图**：以三个边界要点为主，不再拼接重复的产品界面截图；可用简洁线条图标标识“审批、验收、工作区”。

**口述稿**：

Agent 越能做事，越需要清晰的边界。AgentHub 的规划流程保留用户的确认点：先看计划，再决定是否执行，也能拒绝或要求修改。任务还可以带验收标准，最终结果会按这些标准检查，而不是只看 Agent 自己说“做完了”。对工作区操作，文件读写和命令执行要经过沙箱规则；运行端可以接入本地环境。项目的默认形态也是本地运行，不依赖托管服务。这里不是要把所有风险都说成已经解决，而是把关键控制点放在具体流程和执行边界上：哪些任务要跑、谁来跑、在哪个目录操作、结果是否符合约定，都尽量不藏在黑盒里。

**转场**：最后回到开头的问题，AgentHub 想把哪件事变得更简单？

## 幻灯片 9｜让协作从“转发上下文”变成“共同推进交付”

**时间**：7:00–8:00  
**画面文案**：

**提出目标 → 共同澄清 → 计划确认 → 分工执行 → 检查与交付**

底部收束句：**让人把注意力放在目标与判断上，让 Agent 在清楚的边界里接力完成工作。**

**配图**：使用 HTML 内原创 SVG 协作图例，表现“共同对话 → Agent 分工 → 独立产物”，不再重复嵌入产品截图。

**口述稿**：

总结一下，AgentHub 关注的不是让每个 Agent 单独变得更聪明，而是让多个 Agent 围绕共同目标协作时，需求、计划、执行过程和成果都能接得上。用户先提出目标，Orchestrator 帮忙澄清并拆分工作，用户确认后由合适的 Agent 接力执行，最后把结果交付成可查看、可修改的产物。我们希望把人从反复搬运上下文、追问进度和拼装结果里解放出来，让人更多地做目标判断、关键取舍和最终验收。AgentHub 目前已经把会话协作、任务编排、多种 Agent 接入和产物预览连成了一个闭环；接下来最值得继续打磨的，是让这个闭环在更复杂、更真实的任务里依然清楚、稳定、可控。

## HTML 幻灯片制作提示

- 建议 16:9 暖白编辑风格，以墨色标题、蓝绿结构色和少量陶土色为重点。
- 产品截图与原创图例交替使用；同一类应用预览只保留一张，架构和收尾用 SVG 图例讲清关系。
- 每页只保留标题、3–4 个短要点和一个主视觉；完整口述稿放入 speaker notes 或演讲者视图。
- HTML 中的演示截图可点击放大，点击图片或空白处、关闭按钮，或按 Esc 收起。
- 截图均为 3600×2084 左右的宽屏界面（`assert/1.png` 尺寸不同），应使用 `object-fit: contain`，避免裁掉计划卡、产物预览等关键信息。
- 避免把整段讲稿放到屏幕上；用局部放大、描边或编号标出讲述焦点。
- 第 5 页用纯 HTML/CSS 绘制分层流程图，第 9 页用 SVG 协作图例回扣全程。
- 图片可使用仓库相对路径 `assert/1.png` 至 `assert/6.png`；若幻灯片 HTML 不在仓库根目录，需按实际位置调整相对路径。

## 口述自然化建议

1. 把上述口述稿当底稿，不要逐字背诵；每页记住一个结论、一个例子和一句转场即可。
2. 按听众熟悉程度替换“StreamEvent”“SSE”“Adapter”等词；非工程听众可称它们为“统一事件格式”“实时推送”“平台适配层”。
3. 分享前可补一句自己的真实使用感受或现场演示中遇到的一个小问题；只讲亲身经历，不补造数据。
4. 截图里的示例任务有“失败”状态，也有后续成功交付；若现场放图，建议说明这是过程中的一次尝试与迭代，不暗示一次就成功。
5. 页面所列实现情况依据项目 `OVERVIEW.md`、`CLAUDE.md` 和相关 specs 整理；对外分享前可按当日版本更新“当前已实现”的表述。
