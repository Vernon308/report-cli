## 60 秒看懂这场分享

**一句话**：多智能体，就是让一组 AI 像一个团队一样分工干活。这场分享回答一个问题——什么时候该组队，怎么组才不翻车。

**三个关键结论**：

1. 不是所有任务都适合组队。能拆成互不打扰的几块的，组队效果好（不同实验实测提升八到九成）；步骤环环相扣的，组队反而更差（实验中最高倒退约七成）。
2. 翻车的主要原因不是 AI 笨，是系统设计问题：派活没说清楚、信息没传到位、做完没人验收。这三件事都有成熟解法。
3. 我们自己搭了一个多智能体平台（AgentHub），文献里的结论一条条被复现印证，也踩了五个文献没写的坑，解法都会在场上讲。

**术语约定**：全场只需记住三个词——Agent（智能体）= 能自己调用工具、多步执行完成任务的 AI；MAS = 多智能体系统，多个 Agent 协作；token = AI 的计费/计字单位，可以粗略按"字数"理解。其它术语首次出现时，都会当场给一句大白话解释。

## 第一章 概念校准：什么才算多智能体（6 min）

### 1.1 三样容易混的东西

先把三个词分开，后面才不打架：

- **工作流（Workflow）**：步骤事先写死，AI 按流程图走。像工厂的流水线，每个工位干什么是规定好的。
- **智能体（Agent）**：AI 自己决定下一步干什么、用什么工具，干到完成为止。像一个能独立接单的员工：你交代目标，他自己想办法。
- **多智能体系统（MAS）**：多个这样的"员工"，加上一套分工和沟通机制，协同干活。像一个项目组。

两个常见误认顺带排除：把几个 AI 调用串成固定流程，那是工作流不是 MAS，因为没有自主决策；多开几个互不通气的聊天窗口，那也不是 MAS，因为没有分工和协作。

这个区分不是咬文嚼字。我们做 AgentHub 时最早定的一条规则就来自这里：群聊里用户 @ 了某个 Agent，调度器就不插手——用户的显式选择优先于自动调度。"决策权归谁"不定义清楚，这条规则根本写不出来。

### 1.2 为什么一个 AI 不够用

回到开场的举手问题。长任务跑到后半段"失忆"，根源是单个 Agent 有三个硬伤，而且都是结构问题，换更强的模型也治不好：

| 硬伤 | 大白话解释 | 后果 |
|------|-----------|------|
| 上下文爆炸 | AI 的"工作记忆"（上下文窗口）有上限，长任务的中间过程全堆在里面，早期的决定被挤出去了 | 跑到后期"失忆"、跑偏 |
| 职责混乱 | 让一个人同时当调研员、写手和校对 | 角色互相干扰，也没人挑他的错 |
| 无法并发 | 一次只能干一件事 | 本来能同时查的五个方向，只能排队查 |

多智能体的思路，就是绕开"一个人"的极限：让几个 AI 并行干活（省时间）、各自带独立的工作记忆（容量翻倍）、各管一摊事（行为更专注）。补一句实话：这三条硬伤和模型强弱的关系不一样——"上下文爆炸"会随模型窗口扩大而缓解，但"没法并行"和"没人挑错"不随模型变强消失，后两条才是组队的长期理由。Anthropic 打过一个比方：人类个体的智力十万年没多大变化，但组织起来之后，社会的能力是指数增长的。MAS 干的就是把"组织"这件事搬进 AI。

### 1.3 从简单到复杂的五个台阶

多智能体不是一步到位的。Anthropic 把实践中见到的模式按复杂度排成五个台阶，最后两级已经是 MAS 的雏形：

1. **链式（Prompt Chaining）**：任务拆成固定几步，一步一步来。例：先写提纲，检查提纲，再写正文。
2. **路由（Routing）**：先判断问题属于哪类，再分给对应的处理分支。例：简单问题给小模型，难问题给大模型，省钱。
3. **并行（Parallelization）**：几件互不干扰的事同时做，最后汇总。例：三个"审查员"同时检查同一段代码的不同方面。
4. **指挥-工人（Orchestrator-Workers）**：一个"总指挥"看情况临时拆活、派给工人、汇总结果。和并行的区别在于：拆成什么活是现场决定的，事先写不出来。例：改代码——改哪几个文件，得看了需求才知道。
5. **生成-评审循环（Evaluator-Optimizer）**：一个写、一个挑错，改到通过为止。例：翻译、写方案。

同篇文章还有两个实用建议：能简单就别复杂——很多应用把"单次调用 + 检索"调好就够了；慎用现成框架，框架会把底层细节藏起来，出问题难排查，最好先用原始接口自己写，很多模式几十行代码就够。

## 第二章 证据：什么时候有效，什么时候更差（9 min）

这一章全看数据。四组一手材料分别回答：好处有多大、翻车长什么样、边界画在哪、为什么会翻车。

### 2.1 好处有多大

（这组材料只要求听众记住一个数：90%。）

Anthropic 的生产数据：

- 多智能体系统在内部研究评测上比最强单 Agent 提升 **90.2%**（注意口径：这是 Anthropic 自家内部评测）。典型任务："找出标普 500 科技板块所有公司的董事会成员"——单个 AI 一个个查做不完，多个 AI 分头查再做完了。
- 为什么有效？归因分析发现：性能差距的八成，只看谁花的 token 多就能猜到。说白了，**多智能体有效的原因很简单——它能把更多的"算力"花在同一个问题上**。每个子 Agent 有独立的工作记忆，分头探索，只把结论带回来。
- 代价也直接：单个 Agent 的 token 消耗大约是普通聊天的 4 倍，多智能体大约是 **15 倍**。所以这不是免费午餐，是花钱买能力。
- 但要提醒一句：token 解释了为什么**能**有效，却解释不了为什么有人花了 15 倍反而倒退。钱要花对地方——**上限靠投入，下限靠设计**。这正是接下来两个研究要回答的。

### 2.2 翻车长什么样

（这组材料记住：14 种翻车方式。）

Berkeley 的研究者分析了 7 个主流多智能体框架的 1600 多条真实运行记录，把翻车方式归成 14 种、3 大类（论文 arXiv 2503.13657）：

| 类别 | 翻车的样子 | 对应解法（后面展开） |
|------|-----------|---------------------|
| 系统设计缺陷（5 种） | 不按要求做、忘了自己是谁、重复劳动、聊着聊着忘了前文、不知道何时该停 | 把活说清楚、定好停止规则（3.2、4.4） |
| 协作失调（6 种） | 对话被重置、有疑问不问、干着干着跑偏、发现重要信息不告诉队友、无视队友的结论、说一套做一套 | 把信息传完整（3.3） |
| 缺少验收（3 种） | 没做完就交差、交差不检查、检查本身查错了 | 做完必须验收（3.5） |

两个好消息：第一，这些翻车大多不是 AI 笨，是系统设计问题；第二，研究者针对这些问题做了修复（改提示词结构、补验收环节），成功率明显提升。**能被命名的坑，就能被填上。** 表格右列是解法地图，第三到五章逐条讲。

### 2.3 边界画在哪

（这组材料记住一个数：-70%。出现时停顿一下，重复一遍："负七十——选错架构比不做更糟。"）

Google、MIT 等团队做了目前最系统的对照实验（arXiv 2512.08296）：260 种配置、6 个评测基准、5 种架构、3 个模型家族，所有其他条件统一，只看架构差异。结论：

1. **模型越强，组队的相对收益越小**（单体已经够强时，协调是净开销）；
2. **需要频繁调工具的任务，组队反而吃亏**（沟通成本被放大）；
3. **没有独立检查环节的架构，错误会一路传下去**；
4. 任务和架构匹配不匹配，差距巨大：能拆开的金融推理任务，组队提升 **80.8%**；环环相扣的顺序规划任务，组队**倒退 70.0%**。架构选错比不做更糟。（80.8% 是第三方对照实验口径，和 Anthropic 内部评测的 90.2% 条件不同、方向一致。）

可以粗略这样记：多一个人，多一份产出，也多一份沟通开销，而且开销随耦合度非线性上涨——高耦合时，开销能吞掉全部产出还倒贴。这只是个一阶口诀：它预测不了收益递减，也给不了精确拐点（我们平台实测的并行拐点是 4），别拿它当公式真去算。

### 2.4 为什么会翻车：两条直白的原则

Cognition 的文章把机理讲透了。它举的例子：让 AI 做一个"Flappy Bird"小游戏，拆成"背景"和"小鸟"两个子任务分给两个子 Agent。结果一个把背景画成了马里奥风，一个做的小鸟根本不像游戏素材——没法拼到一起。

两条原则：

1. **信息要传完整的记录，不是转述几句话。** 你只告诉同事"做个背景"，他当然按自己的想象做。
2. **每个行动背后都有没明说的决定。** 两个子 Agent 在互相看不见的地方各自决定了风格，合并时必然打架。

所以 Cognition 的建议是：默认让单个 AI 按顺序干；活太长就用专门手段把"之前做过的决定"压缩传递下去。现在可以回答序章的争论了：Cognition 反对的不是多智能体，是"随手拆活、只传消息"的偷懒做法；Anthropic 也承认编程任务能并行的部分少。两家说的是同一张地图的不同区域。

### 2.5 一句话判据

能不能组队，核心变量是**耦合度**——这些活能不能分给几个人同时干、互相不用等对方？能，收益为正；不能，收益为负（Google 的实验里，高耦合的顺序规划任务最高倒退了约 70%）。完整四步判断在终章：先确认单干撞墙，再看耦合度。

## 第三章 机制：组队要解决的五件事（11 min）

把 AI 团队真组起来，要回答五个问题：谁听谁的（分工结构）、活怎么派（任务分解）、信息怎么给（上下文）、话怎么说（通信）、活怎么验（验收）。每件事按固定节奏讲两遍：先看论文怎么说，再看我们怎么落地；幻灯片右上角始终标出"五件事地图"的当前位置，听众不容易跟丢。

### 3.1 分工结构：三条路线

| 路线 | 怎么运转 | 谁在用 | 特点 |
|------|----------|--------|------|
| 中心化 | 一个"总指挥"统一拆活、派活、收结果 | Anthropic、OpenAI Manager 模式、AgentHub | 好管理、好验收；总指挥是瓶颈 |
| 去中心化 | 几个 AI 平级，谁擅长谁接，干完转给下一个 | 客服系统的"转接"模式 | 对话场景自然；转接条件写不好会来回踢皮球 |
| 混合 | 总指挥管大方向，小组内部自治 | Claude Code、大型团队 | 适合大团队；层级多了会慢 |

这个"中心化/去中心化/混合"的划分，和学界综述的分类基本一致（arXiv 2501.06322）。我们选了中心化，原因很实际：第一版必须能"审批"——中心化结构里，计划是天然的审批点；去中心化的转接想加审批，都不知道该在哪拦。**涉及钱和写操作的场景，首选"中心化 + 关键环节人点头"。**

### 3.2 派活：把"说清楚"变成格式

文献做法（Anthropic 用翻车换来的）：派活必须说清四件事——**干什么、交什么样、用什么资料、别碰什么**。反例是他们自己的：总指挥只说"研究一下半导体短缺"，结果三个子 Agent 两个重复查今年的供应链，一个跑去看 2021 年的旧闻。另外，干多大规模的活也要给刻度：简单查询 1 个 Agent、调 3 到 10 次工具；对比类任务 2 到 4 个子 Agent、各 10 到 15 次调用；复杂调研 10 个以上且分工明确。AI 自己不会掂量该花多大力气，必须给数。

这四件事在生产系统里长什么样？这是 AgentHub 里"派单"工具的真实格式：

```json
{
  "reasoning": "为什么这样拆",
  "tasks": [{
    "id": "t1",
    "agentId": "谁干",
    "task": "干什么",
    "dependsOn": ["t0"],
    "inputs": ["要用上游的哪个产出"],
    "expectedOutputs": [{"outputKey": "prd", "type": "document"}],
    "constraints": ["范围仅限订单模块", "不许改公共组件"]
  }]
}
```

看不懂细节没关系，它的意思就是一张**派工单**：干什么（task）、谁干（agentId）、交什么样（expectedOutputs）、等谁先做完（dependsOn）、别碰什么（constraints）。文献说的四要素全在里面，只是从"提醒 AI 注意"变成了"系统能检查的格式"。另外，计划生成后会**先停下来等人审批**，批准前不许动工——机制上掐断，不是靠自觉。

### 3.3 通气：给多少背景，是个精细活

文献做法：要给就给完整的记录，别只转述结论；重要计划要写到外部存储里，因为工作记忆超限会被截断；长任务分段接力。

实战形态。AgentHub 的子 Agent 上岗前，收到的不是群聊全部历史，而是一份"入职简报"。简报就三条规则，每条都是踩坑踩出来的：

- 消息只留**最近 5 条 + 置顶**——再多就是干扰；
- **依赖链上的上游产物**给摘要、需要全文自己调工具取——专防"发现重要信息不告诉队友"（第二章"协作失调"类翻车），全文塞进简报会把工作记忆撑爆；
- **其它产物只给标题**——知道存在就行，要用再取。这就像带新同事：给他一份一页纸的简报加关键文档清单，而不是把公司十年邮件全转发给他。有听众可能会问：2.4 不是说"信息要传完整记录"吗？这里裁的是噪音，不是决定——依赖链上的上游产物和关键决定，全文随取随有；和任务无关的群聊闲聊，才主动挡在门外。

### 3.4 对话：行业已经有"普通话"了

工程上的共识：Agent 之间用**异步消息**沟通（留字条，不当面喊话），汇报用**结构化格式**（填表，不写小作文）。

标准协议也已经分层，可以理解为 AI 世界的"普通话"：MCP 管"AI 连工具"（像 USB 接口，一个标准处处能用）；A2A 管"AI 连 AI"（2026 年 4 月发布 v1.0，150 多家公司支持）；AG-UI 管"AI 连人"（把过程和结果呈现给用户）。

A2A 里有个设计值得记住：对方 Agent 对你是**黑盒**——你能用它，但看不到它的内部数据和工具。这恰恰是跨公司、跨部门协作的信任基础，就像你可以请外包干活，但不用把自家账本给他看。

我们平台在通信层的落地：全系统由一套统一事件模型驱动，子 Agent 的每条进度都作为事件转发进主事件流，用户在一个界面看到所有 Agent 的实时状态；下一节的"完工单"就是"结构化汇报"的落地——汇报不是自然语言小作文，是带验收条件的固定格式。

### 3.5 验收："做完了"三个字不算数

文献做法：Google 的实验证明，没有独立检查环节的架构，错误会一路传下去；Anthropic 的报告要过独立的"引用核查员"逐条核对；验收只看最终结果对不对，不纠结过程。

实战形态：AgentHub 规定子 Agent 收工必须填"完工单"（`report_task_result`），**状态写"完成"且验收条件逐条通过，才算完成**；没填单、报失败、任何一条验收没通过，一律按失败处理。

这就像装修验收：师傅说"装完了"不算，照着验收单一项项打勾才算。没有这张单子，总指挥汇总的就是一堆半成品。

## 第四章 生产的距离：从能跑到敢上线（8 min）

### 4.1 一个生产级系统长什么样

以 Anthropic 的调研系统为例，完整链路六步：

1. 收到问题，创建"主研究员"，先想策略，并把计划写到外部存储（防工作记忆超限丢失）；
2. 典型问题派出 3 到 5 个子 Agent 分头搜索（超复杂的可以到 10 个以上，刻度见 3.2）；
3. 子 Agent 像"智能过滤器"：边搜边评估质量，只把精华带回来；
4. 主研究员汇总，觉得不够就再派人；
5. 材料齐了，交给独立的"引用核查员"逐条核对出处；
6. 输出带来源标注的报告。

速度从哪来？两层并行：主研究员同时派多个人，每个人同时调多个工具。复杂调研的时间最多省 90%——从几小时压到几分钟。

### 4.2 提示词工程：八条实战经验

多智能体的提示词，写的不是"更严格的指令"，而是"团队协作章程"：谁干什么、怎么干、花多少力气。Anthropic 的八条经验如下，现场建议只展开 1、4、6 三条（最有画面感），其余每条一句话带过——8 条全讲会信息过载：

1. 用和线上一模一样的配置搭个"沙盘"，看 AI 一步步怎么干活——很多问题看一遍就明白了；
2. 派活说清四件事（3.2）；
3. 干多大规模的活给明确刻度（3.2）；
4. 工具说明书写清楚，就像给人用的产品说明书——说明书写得烂，AI 一定用错；
5. 让 AI 改 AI：做一个"工具测试员"，反复用有问题的工具、然后重写说明书，后续任务时间降了 40%；
6. 搜索先宽后窄：先撒网看全景，再深挖（AI 天生爱一上来就问得又细又窄，要纠正）；
7. 让 AI 把"思考过程"写出来，当草稿纸用；
8. 上限和停止条件写进章程，别指望事后补救。

### 4.3 怎么判分：路不只一条时

多智能体评测的难点：同样到达终点，走的路可以完全不同。没法用"标准步骤"卡它，只能看结果。做法：

- 评测别等完美了再建：早期一次调整能把成功率从 30% 提到 80%，20 条真实问题就能看出变化；
- 用 AI 当裁判可以规模化：定好评分细则（内容准不准、引用对不对、全不全、来源好不好、工具用得省不省），一次调用出分加通过判定，和人工打分高度一致；
- 人工抽查不能省：人发现过 AI 裁判漏掉的问题——系统偏爱 SEO 优化过的"内容农场"，而不是权威但排名低的学术文档，后来专门补了规则；
- 看最终结果加关键节点，不看逐步过程。

### 4.4 可靠性：四个上线级挑战

Anthropic 的原话："最后一公里往往是旅程的大半。"

1. **小错会滚雪球。** AI 干活是连着几十步的，一步出错后面全歪。对策：出错从断点续跑（不从零重来）、定期存"存档点"，还有个反直觉但好用的招：告诉 AI"这个工具坏了"，让它自己想办法绕过去。
2. **老办法调不了新问题。** 同样的指令每次表现都可能不同。对策：全程留痕（tracing），记录"做了什么决定、和谁交互"，而不是记录聊天内容本身——既能排查又保护隐私。
3. **不能停机升级。** 系统里随时有正在跑的任务。对策：新旧版本同时跑，流量慢慢切过去（彩虹部署）。
4. **排队等待有瓶颈。** 总指挥等一拨人全干完才能继续，一个慢的全局都等。方向是异步执行，但协调难度更大，这是行业下一步要啃的骨头。

实战印证：AgentHub 的执行是"按依赖排队 + 同批并行"：有依赖的排队，没依赖的同时跑，**全局并行上限设为 4**；上游挂了，下游直接跳过。这个 4 是试出来的：再大，几个 AI 抢资源的抖动就把并行省下的时间吃掉了——就像厨房同时炒 4 个菜刚好，8 个就开始糊。

### 4.5 成本：上线前就要算的账

- 量级：多智能体约是聊天的 15 倍 token。成本要在设计阶段摆上桌面，不是上线后再压。换算一下口径：多智能体约为**单干的 3~4 倍**（15 对 4），定红线要用这个数，别拿对聊天的 15 倍吓自己。
- 派活刻度（3.2）是最直接的阀门：小活不派大队。
- 缓存就是钱：Claude Code 让子 Agent 复用父 Agent 的"前文缓存"，成本降到约十分之一。好比复印材料时，前半本和原来一样就不用重印，只印不同的几页。便宜九成，就敢更频繁地派活。
- 工具说明书写好，任务时间省 40%——AI 纠错也是要花 token 的。
- 实战：AgentHub 把每次运行的输入/输出/缓存 token 分开记账。没有这本账，"成本不许超过单干两倍"这条红线根本无从检查。

### 4.6 状态：老纪律全都用得上

多智能体规模化后，就是个分布式系统，老一代分布式系统的纪律全部适用：

- 全局信息只有"总指挥"能改，干活的只能追加汇报（防止多人同时改乱）；
- 写操作要防重：同一件事重复提交不会执行两遍（幂等）；出错要能按相反顺序回滚（补偿）；关键节点留人审批；
- 高频翻车点：没完没了地重新规划（铁律：重规划最多 3 次）；转接条件含糊导致来回踢皮球；写操作不防重导致重复执行；把"再试一次"当成"会自我改进"——没有验收标准的重试，纯烧钱。
- 记账方式用"事件溯源"：不记最终状态，只记发生的每件事，机器挂了换台机器把记录重放一遍接着干，不重复花钱。

（现场节奏提示：这一节只展开"重规划最多 3 次"一个数字，其余纪律一句话带过——分布式老手自然懂，新手记住"老纪律全适用"即可。）

实战形态：AI 生成的派工单，系统用确定性代码逐条校验——编号不能重复、不能自己依赖自己、不能循环依赖、执行人必须在场。规则都不复杂，但少一条，执行阶段就会用更贵的方式爆掉。

## 第五章 实战复盘：文献没告诉我们的五个坑（7 min）

这一章全是自己的。AgentHub 是我们自建的多智能体协作平台（形态像群聊：Agent 是群成员，总指挥是群里的项目经理）。文献的结论在搭建中一条条被复现印证，但真正长记性的是这五个坑。

**坑一：AI 派单会漏写依赖关系。** 比如明明"B 要用 A 的产出"，它就是不写。在提示词里反复强调没用——这不是态度问题，是生成的不确定性。解法：用确定性代码兜底，从任务顺序和文本信号（"基于 t1 的产物"这类字样）自动补全依赖。**认知：AI 的输出永远当草稿，不当真相；结构性约束必须代码兜底。**

**坑二：规定了格式，AI 照样写歪。** 我们的"写产物"工具有严格格式约定，但 AI 有时给这种结构、有时给那种、有时干脆一段裸文本。早期是格式不符就报错，用户看到一堆莫名其妙的失败。解法：入口处做兼容，几种常见形态都接受、自动归一，实在不行才报错。**认知：对 AI 的输入容错，要比对人的输入容错做得更宽——宽进严出。**

**坑三：并行改同一个文件，只能提醒，不能代劳。** 两个子 Agent 同批干活，可能同时改同一个文件。系统会检测并报告冲突，但我们选择**不自动合并**——合错了比冲突本身更难查。**认知：有些问题别急着自动化解决，先让它可见。可见的问题人能处理，看不见的问题才是事故。**

**坑四："我做完了"没有意义。** 早期子 Agent 说一句完成，总指挥就采信，汇总时频繁拿到半成品。加上"完工单 + 逐条验收"后彻底改变（3.5）。**认知：验收标准不是流程装饰，是协作协议的一部分。这也解释了为什么"缺少验收"是学术统计里的高发翻车——多数系统根本没给 AI 装"自证完成"的通道。**

**坑五：审批不是在界面上加个按钮。** 第一版审批就是界面上一个确认框，结果拦不住：用户还没看完计划，执行消息已经刷出来了。真正的解法是在机制层面：系统一旦看到"派单"动作，直接停止接收后续输出，从根上保证"批准前无动作"。**认知：留人把关是架构属性，不是界面属性。拦不住机器的审批等于没有审批。**

**实战与文献对照**（一页讲完的版本）：

| 文献说 | 我们验证到 |
|--------|-----------|
| 派活要给明确边界 | 派工单里的产出要求、依赖字段就是边界的具体形态 |
| "信息截留"是高频翻车 | 简报里只注入依赖链上的上游产物 |
| 独立检查抑制错误传播 | 完工单 + 逐条验收，前置把关 |
| 协调有开销 | 并行上限实测到 4，再大反而慢 |
| 成本要可计量 | 输入/输出/缓存分开记账，红线才检查得了 |

## 终章：把判断和顺序带回去（3 min）

**四步判断法**（该不该组队）：

1. 单个 Agent 榨干了吗？没撞墙别组队。撞墙信号就两个：逻辑复杂到提示词里全是分支；工具职责互相重叠（经验值：15 个清晰的工具管得住，10 个重叠的就失控）。
2. 活能拆开吗？几部分互不干扰、能同时干，才值得拆；环环相扣就留在单线程。
3. 门槛过了吗？单干成功率先到 80%；组队的完成率至少高 5 个点；成本红线按自己场景定——文献里重调研场景约为单干的 3~4 倍，我们平台任务短、有缓存复用，定在 2 倍以内。
4. 验收进架构了吗？独立检查、写评分离，从第一天就放进去。

（现场留 30 秒：请每位想一个自己手头的任务，心里过一遍第 1、2 步——信息卡承诺的"当场能算"，必须真的发生。）

**动手顺序**（我们自己走过的）：单 Agent + 原始接口 → 攒 20 条真实问题建评测 → 加"总指挥 + 计划审批" → 上任务契约（产出要求/依赖/验收条件）→ 定并行上限和失败规则 → 补冲突检测、token 记账、全程留痕。每步都有产出，不存在"平台建成才能用"的阶段。

**开放问题**：如果你的团队明天多出五个不知疲倦的"数字同事"，你第一件事会教它们什么？
