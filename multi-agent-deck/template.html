单个 Agent 的三大局限

01 · Why one is not enough
Limit-01

上下文装不下

多阶段任务里，对话历史越滚越长，模型开始「丢三落四」。

阿里的典型例子：「金额字段统一 DECIMAL(22,6)」写在最开始的提示词里，跨过 30 轮对话、5 个阶段之后，模型就忘了。

不是模型变笨 —— 是注意力机制天然不擅长保持长程约束。

Limit-02

既当运动员
又当裁判

让同一个 Agent 又写代码、又评审自己的代码，它很难发现问题。

这不是态度问题，是认知偏差。

生产对策：写的人和评的人，必须是两个 Agent。

Limit-03

只能串行

一个 Agent 一次只能干一件事。三个模块的活：

串行
10 min
并行
3 min

串行 10 分钟的活，并行只要 3 分钟。

案例 · 腾讯 Marvis（应用宝端侧助手）
文件知识库、操作系统理解、APP 操控 —— 三个不同领域的活全塞给一个模型：上下文爆炸、只能串行、调度复杂。所以一上来就选多智能体主从架构：不是炫技，是问题逼的。

六种队形：组织方式决定协作上限

02 · Patterns

Supervisor 主从式

项目经理带队员

协调者拆任务、派活、收结果、汇总。生产环境绝对主流：Claude Code 子代理、LangGraph、CrewAI 全收敛于此。可控，但协调者耗 Token、易成单点瓶颈。

Hierarchical 层级式

部门层级：总监管经理

团队大了就分层：总监管经理、经理管队员。适合大规模跨领域协作；代价是层间传递慢、每层管理者的指令都更难写。

Pipeline 流水线

提取 → 转换 → 校验

一道接一道，最简单、最好排查问题；但没法并行，上游堵了下游只能干等。

Peer-to-Peer 圆桌讨论

互相辩论、交叉评审

适合离线评审：方案比选、代码审查。毛病是聊个没完 —— 成本约单模型 2.5×，只有高风险决策才值得用。

Swarm 工单转交

「处理不了，转给二线」

没有总调度，直接交接，比主从省一次中转、延迟低。最大的坑是循环转交：A→B→A 无限乒乓，生产上必须设转交上限。

Dynamic 动态路由

来什么活，派什么人

路由角色先判断任务类型再分发。适合请求类型差异大的场景；代价是路由逻辑本身要持续维护。

毕马威 · 银行业调查
金融行业同样归纳为四种联动模式：层级式 · 流水线式 · 交接式 · 辩论式 —— 按业务场景选用

3.1 隔离：各干各的，互不干扰

Mechanism 1 / 5 · Isolation
Claude Code · 按每个状态的语义，单独决定隔不隔离
  • 读文件的缓存 —— 克隆一份给子 Agent
  • 写全局状态的权限 —— 直接收回：子 Agent 的写操作变成空调用
  • 任务注册的通路 —— 保留
工具的三道准入门
① 拉黑「能派新子代理」的工具，防递归派生失控
→
② 按自定义 Agent 再加严
→
③ 白名单放行
Anthropic · 更彻底的做法

每个子 Agent 拿到
全新的空白上下文

  • 不带协调者的对话历史
  • 故障隔离：一个子 Agent 跑偏，不污染别人
  • 也让并行执行成为可能
一句话总结
隔离的目的不是「隔得越远越好」，
而是让每个 Agent 只看到它该看到的

3.2 通信：异步 + 消息

Mechanism 2 / 5 · Communication
反例 · 为什么不用函数调用

父 Agent 调子 Agent、等它返回 —— 同步调用会把父 Agent 卡死几分钟，五个子 Agent 被迫串行。这条路走不通。

实际做法 · 消息信箱 Mailbox
  • 父 Agent 把消息写进子 Agent 的待收队列就返回 —— 不等
  • 子 Agent 每轮循环检查信箱，把消息当成一条新的用户输入来处理
  • 子 Agent 已停止？发信自动从磁盘恢复历史，把它唤醒
  • 干完活，拼一段结构化 XML 送回：任务编号 · 状态 · 结果摘要 · Token 用量 · 耗时
为什么用结构化格式，而不是自然语言
8% → 1% Anthropic 实测：Agent 之间改用
JSON Schema 契约交接后的错误率

阿里走得更远：Agent 之间干脆不直接对话，全部通过预定义格式的结构化文件交换信息 —— 可追溯、可审计、可恢复。

澄清两个常混的协议
MCP
Agent ↔ 工具之间的连接
类比 USB 接口 —— 在下层接工具
A2A
Agent ↔ Agent 之间的互操作
类比 HTTP —— 在上层做编排

一个在下层接工具，一个在上层做编排 —— 不是一回事。

3.4 调度：协调者到底该干什么

Mechanism 4 / 5 · Scheduling

收结果

手里只有四个工具
建队 · 解散 · 发消息 · 合成输出
协调者必须「理解」而不能「转发」 —— 如果只是转发，它就没有存在的价值。
流水线四阶段
调研（Worker 并行）→ 合成（协调者亲自写规格，不外包） → 实现（Worker）→ 验证（Worker）
值得记住的细节
  • 验证永远派新 Worker —— 不能让干活的自己验自己
  • 新任务与某 Worker 上下文高度相关 → 接着干；不相关 → 派新的
  • Worker 不许再派 Worker —— 收回派生权限，扁平一层，防嵌套失控
  • 派活时把目标、输出格式、边界写清楚 —— 指令模糊 = 重复劳动 + 盲区

3.5 成本：跑得起，才算数

Mechanism 5 / 5 · Cost
多智能体的账，这么算
单 Agent 成本 = 每轮 Token × 轮数 × 单价
多 Agent 成本 = Σ Worker Token + 协调者 Token × 轮数 + 合并开销
上线前先过 ROI 门槛：完成率比单 Agent 高 5 个百分点以上、成本控制在 2 倍以内，才放行。
80%
影响多智能体系统性能的因素里，Token 用量独占 80% 的解释力，其余是工具调用次数和模型选择 —— 本质是拿 Token 换性能。
怎么把成本压下来 · 业界三招
① 缓存复用 · Fork 机制

Prompt 缓存只要请求前缀逐字节相同就命中，命中后价格是一折。Fork 的子 Agent 完整继承父上下文前缀 = 花十分之一的价钱复制一个「分身」。

「原本因为成本不敢派的活，现在都敢派了 —— 这反过来扩大了系统的能力边界。」

② 按任务定配置

规划用强模型、执行用便宜模型；简单任务少派人，复杂任务多派人。

③ 允许部分失败

个别子 Agent 超时（约 2–3%），用已完成的结果继续合成、标注哪块缺了 —— 而不是整体重来。

4.1 约束不是束缚，是保险带

阿里数据研发团队 · 约束金字塔
约束分三层 · Constraint Pyramid
「约束不是为了限制能力，而是为了让能力稳定地释放出来。约束越清楚，采样空间越聚焦，输出的方差就越小。」
更直白地说：可控，比聪明更重要。
配套 · 门禁制度 Gatekeeping
  • 流程设 8 个关键检查点，强制检查项不给 Agent「我觉得不需要」的权力
  • 写的人和评的人分开 —— 生产者与评审者必须是不同 Agent
  • 1688 原则：往前走必须有人点头，打回来直接改不用再审批 —— 正向流转必须审批，回退路径放开
  • 每个环节最多返工 3 次，超时人工介入

4.3 规模上来之后：这其实是分布式系统

几百上千个 Agent · 7×24 运行
业界参考架构 · 五层
① 接入层异步网关：收到请求先登记、立即返回，结果走推送通道 —— 避免长连接被拖垮
② 通信编排层分布式事件总线（Kafka / Redis Streams），发布订阅，靠单调递增序列号保证消息不乱序
③ 执行层无状态的 Agent 集群 —— 哪个节点空闲，哪个接活
④ 状态层Redis 管活跃状态，PostgreSQL 存事件日志
⑤ 记忆层短期记忆放 Redis；长期记忆（用户画像、审计日志）放向量库
很妙的机制 · 钝化与唤醒 Passivation
Agent 等大模型返回的几十秒
→
上下文转储到状态层，释放算力
→
结果到达，任意空闲节点捞回上下文接着跑

操作系统换页、Akka 的 Actor 钝化 —— 都是同一个思想。

限流防雪崩

几百个 Agent 同时调同一个模型的 API-Key，触发限流就是雪崩。解法：给每个模型供应商建一个「虚拟令牌池」，下游返回限流信号时队列自动放慢投递，配合指数退避重试。

多智能体架构，本质上是把分布式系统的老坑重新踩一遍 —— 幂等、补偿、事件溯源，全是熟面孔。

05 · 协同的另一半：人和制度

瓶颈常常不在 Agent，在人
快手量化分析
30%
工程师一天真正写代码的时间；其余 70% 花在需求对齐、沟通、交接上
AI 压缩编码时间、协作时间不变 → 收益被稀释：代码生成率 17% → 30%，交付周期几乎没变。
个人提效 ≠ 组织提效
人机协作的四类摩擦
  • 人给 AI 当「搬运工」，手动补上下文
  • AI 几分钟生成，人花几小时验证
  • 对能力边界没数：低估错过效率，高估导致返工
  • 根子：研发体系是围着人设计的 —— 信息按人的分工切块，AI 拿不到完整上下文；流程按人的节奏串行，并行优势发挥不出
人的角色整体上移
  • 腾讯：人不是从系统里退出，而是从处理任务转向建设任务系统

审批与风险
控制缺位

痛点 2.4

并行缺少
统一视图

五条措施：从「零散日志」到「结构化工作空间」

Part 02 · 怎么做
措施一

以「会话」而非「日志」组织工作

消息按结构化 Parts 分类渲染：文本说明 / 代码片段 / 思考过程 / 工具调用 / 执行结果 / 产物引用，各自独立展示。检索「某一步做了什么」，直接定位消息类型，不在大段日志里逐行翻找。

措施二

文件与产物纳入「共享工作区」

每个任务绑定明确的工作区目录，所有读写限制在目录范围内 —— 从机制上避免误改其他项目。文档、图片、代码、部署预览统一以「产物卡片」挂载在会话里，点开即可预览。

措施三

高风险操作前置审批

批量写入、敏感命令、正式发布：加一个轻量「审批模式」开关 —— 执行前弹出确认卡片、列明操作内容，批准后才真正执行。把「先斩后奏」变成「先审后行」。

措施四

任务可拆分、可并行、可汇总

引入「协调者」角色（人工 PM，或具备编排能力的工具 / Agent）：拆解大任务 → 分发给人或工具并行处理 → 自动跟踪各子任务的完成 / 失败 / 阻塞状态 → 全部完成后自动聚合为一份结构化总结 —— 减少「逐个催进度、手动拼结果」的沟通成本。

措施五

本地优先、数据自主可控

核心数据 —— 会话记录、密钥、工作区文件 —— 默认保存在本地或团队自有环境，不依赖第三方托管服务。兼顾协作效率与数据安全合规，尤其适合对数据出境、第三方存储有严格限制的场景。

为什么这样设计：五个设计决策

Topic 02 · Design Decisions
Runtime不是运行时容器，而是能力目录 + 运行编排：每个 AI 能力建模为可注册、可路由、可回流的「运行会话」，系统知道「当前在跑什么、跑到哪了、产出是什么」。
注册化新增一个 AI 能力只需登记能力定义 —— 运行中枢与前端壳零改动，自动接入同一套工作区、会话与回流机制。
Runner+Ucode直接调 LLM 只能回答问题；走 Runner + Ucode 智能体才能读代码仓库、产出可落库的流程对象 ——「聊天」和「进入研发管理流程」是两件事。
人工确认AI 不知道组织内部的优先级、资源约束和隐性规则 —— 人工确认不是不信任 AI，而是把最终决策权和管理责任留在人手里。
结构化输出自然语言聊天结果不可复用、不可校验；结构化输出才能落库为流程对象，被后续拆解、文档、巡检复用。

边界与规划：AI 不做什么，下一步去哪

边界 ①

资产质量是上限

需求不完整、文档缺失、任务混乱、代码复杂 —— Agent 建议质量都会下降。资产治理与 Agent 建设同等重要。
